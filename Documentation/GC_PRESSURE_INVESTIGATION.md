# GC pressure investigation

October 14, 2026. Source review and Unity 6000.4 documentation review. Terrain-worker native allocation lifetimes corrected and padded control-map scratch reuse added; no collector policy or gameplay settings changed.

## Padded control-map scratch reuse

Each `TerrainRequestManager` now owns a `TerrainControlMapScratchPool` with capacity equal to its sanitized terrain-data worker limit. The first padded map dimensions fix the pool's retained shape. Buffers are allocated lazily; different dimensions or excess simultaneous borrowers receive fresh, unpooled scratch rather than growing the retained pool or waiting for a buffer. There are no global size buckets. Shutdown drops idle references, and late worker returns do not revive the pool.

`TerrainControlMapBuilder.BuildRaw` borrows the three padded `Color32[]` maps and clears them before filling. Clearing is required because material writes leave some maps/channels untouched. A `finally` returns borrowed scratch after blending, including when building fails. The three blended result arrays remain newly allocated and independently owned: queued results and texture publication never reference scratch that another worker can overwrite. Existing callers that omit the optional pool keep the fresh-allocation path.

For the normal 131-square padded input, this avoids repeatedly allocating **205,932 bytes (about 201 KiB)** of pixel payload per chunk after warmup, plus the scratch object's/jagged array's/three pixel arrays' headers. The 129-square output still allocates **199,692 bytes (about 195 KiB)** of pixel payload. A four-worker pool retains at most **823,728 bytes (about 0.79 MiB)** of scratch pixel payload until manager shutdown. These byte figures are calculated from array sizes, not measured profiler byte totals.

The tradeoff is bounded retained memory, array-clearing work and short borrow/return locks on workers. This reduces temporary managed allocation churn; it neither spreads collections across frames nor guarantees a smaller GC pause. Other terrain maps and the explored-chunk cache remain much larger memory contributors.

Profiler samples `FS.Streaming.Worker.ControlMapBuild` and its nested `FS.Streaming.Worker.ControlMapScratch` appear under `FS.Streaming.Worker.TerrainDataRequest` on the relevant Scripting Thread Pool Worker. The scratch sample includes borrowing/allocation and clearing; the build sample also includes filling, blending and snow overlays. Compare warmed builds separately from the initial pool allocations.

Run **Tools > Terrain > Validate Control Map Scratch Reuse** for pixel equality across dirty reuse, forest/snow/material inputs, output independence, failure cleanup, simultaneous workers, capacity/shape bounds and shutdown. Its allocation check uses Unity's current-thread `GC.Alloc` event recorder, without frame aggregation. `GC.GetAllocatedBytesForCurrentThread` returned zero in this Unity Mono runtime; `GC.Alloc` recorder values are timing samples, so the fixture counts allocation events instead of reporting those values as bytes. See [Unity's current-thread recorder example](https://docs.unity.com/en-us/engine/6000.5/script-reference/unity/profiling/profilerrecorderoptions/collectonlyoncurrentthread).

Validation passed in Unity 6000.4.8f1: warmed builds produced **10 allocation events before reuse versus 5 after reuse**, over eight builds per path. Runtime/editor/player compilation passed. The isolated batch also passed streaming/architecture/foliage/grass/Inspector regressions and real terrain-worker lifetime checks; log: `.utmp/streaming-budget/control-scratch-validated.log`. No live traversal or GC-pause benchmark was run. Restart Play Mode after import, repeat the same route and inspect the new worker markers, allocation rate and GC peaks to assess the frame-time benefit.

## Assessment

Subsequent ownership cleanup added full generated-resource disposal, guarded explicit chunk retirement, consumer-reference cleanup, request invalidation and late-result/shutdown handling. Tree placements remain registered and no automatic eviction policy is enabled, so exploration still retains cached regions unless explicitly retired. See [Terrain ownership](TERRAIN_OWNERSHIP.md) for lifecycle contracts and validation.

The user supplied a concrete Console diagnostic during the investigation: a native allocation was disposed at age seven frames, beyond its TempJob four-frame lifetime. Its stack points to the mountain-mask disposal in `TerrainRequestManager.RequestTerrainData`. This establishes an allocator lifetime mismatch and a source of warning/stack-trace overhead; it does not prove that all stack traces or the 9.49 ms managed GC pause have the same cause.

The reported request's eight scratch buffers now use Persistent allocation with existing explicit ownership/finally cleanup. The mountain-mask buffer is released immediately after biome classification; seven ecology inputs are released after the ground-cover job, before snow/control-map generation. Retained-map height/climate worker scratch and snow job scratch also permit multi-frame lifetimes. Persistent permits the lifetime; it does not mean the buffers are kept forever. Allocation/deallocation may cost more than TempJob, so compare a new capture. These changes target normal terrain-data workers; other generation paths still require separate lifetime audits if warnings identify them.

Runtime, editor and player C# compilation passed. The real-request integration fixture passed with full leak stack tracing, delayed output retention, native/managed sample agreement and no lifetime diagnostics (`.utmp/streaming-budget/worker-lifetime.log`). This validates the isolated fixture; it does not reproduce all timing/contention conditions from the user's slow frame or establish a measured GC-pause reduction.

The architecture/streaming/foliage/grass/Inspector suite also passed with the corrected code (`.utmp/streaming-budget/gc-fix-streaming.log`). Stop Play Mode before invoking the worker fixture from its Tools menu so it does not compete with a running world's requests.

The broader `WorldErosionValidation` suite failed its far-terrain maximum-vertex-spacing assertion. Repeating that suite with the original HEAD versions of all four files changed by the allocator fix produced the same failure. Logs: `.utmp/streaming-budget/gc-pressure-regressions.log` and `gc-baseline-erosion.log`. That existing failure limits the broader numerical validation; it was not repaired as part of this GC investigation.

See [Unity allocator guidance](https://docs.unity3d.com/Packages/com.unity.collections@6.4/manual/allocator-overview.html). Run **Tools > Terrain > Validate Terrain Worker Allocation Lifetime** for real requests across Editor updates with leak stack tracing enabled and eight-update output retention. Do not disable lifetime warnings to hide this mismatch.

Custom scheduling may improve when GC runs, but it still invokes Unity's collector. It cannot guarantee that every collection becomes a bounded slice. Start with diagnostics, allocation reduction and bounded retention; compare automatic scheduling with an optional player-only policy after establishing a clean baseline.

The supplied captures show a 9.49 ms main-thread collection, 0.35 ms result publication, 0.11 ms terrain content, 1.34 ms grass streaming, significant EditorLoop time, worker-side stack-trace extraction, and an all-thread allocation burst. They do not establish why this collection was long, the runtime incremental mode/slice duration, the stack-trace caller, or a causal link between that frame's allocations and its collection. ## Verified project findings

- `ProjectSettings/ProjectSettings.asset` enables incremental GC (`gcIncremental: 1`). No explicit `GC.Collect`, `CollectIncremental`, GC mode assignment or slice-duration assignment was found in `Assets/Scripts` or `Assets/Editor` during this investigation.
- Both saved quality levels have `vSyncCount: 0`; no `Application.targetFrameRate` assignment was found in project C# code. External/runtime overrides remain possible. The Profiler's Highlights target of 120 FPS is an analysis threshold, not a game frame-rate cap. An actual frame-rate target may provide spare frame time that Unity can use for GC.
- SmearScene uses 128-sample chunks and up to four concurrent terrain-data workers. Each padded map is 131 by 131. One float map's payload is 68,644 bytes (about 67 KiB), excluding object headers.
- `HeightMapGenerator.GenerateTerrainHeightFieldCore` allocates four managed maps and native job buffers. `ClimateGenerator` allocates two additional managed maps while retaining native outputs for the request pipeline.
- `WorldFeaturePlan` allocates two float maps plus nine forest and six grassland float maps. Those 17 float maps alone total about 1.11 MiB per plan at this resolution. Membership, optional floor ecology, placement lists, terrain/climate/classification maps and native copies add more. These are source-derived payload estimates, not profiler measurements, and much of this data is retained rather than immediately becoming garbage.
- Before scratch reuse, `TerrainControlMapBuilder.BuildRaw` allocated three padded pixel buffers, then three blended buffers: combined payload 405,624 bytes (about 396 KiB) at 131-square input and 129-square output. The padded set is now pooled for normal requests, leaving the independently owned result allocation. `MountainSnow.Generate` still creates a temporary managed float2 map.
- `ChunkManager` retains normal chunk records in its dictionary after runtime unloading. `GetOrCreateChunkRecord` adds records, while shutdown disposes their native data. There is no normal chunk-data eviction policy in that coordinator. Live cached maps cannot be reclaimed by running GC more often.
- The new completion-backlog guards constrain further dispatch after publication falls behind. They do not rate-limit managed bytes allocated per second, and completed-job limits do not bound the total explored-world cache.

## Strategies, in recommended order

1. **Identify diagnostic overhead.** Determine whether worker stack traces come from Console errors, native leak stack tracing, or allocation call-stack capture. Resolve actual errors. Compare native leak detection with versus without stack traces while retaining basic detection. Keep allocation-stack captures short and separate from performance baselines.
2. **Reduce temporary allocation bursts.** Pool worker-owned scratch maps and padded control-map buffers with explicit disposal/return on success, failure and cancellation. Keep buffers owned by queued results until publication releases them. A fixed-size or bounded pool prevents converting transient garbage into an unbounded retained heap. Consider native-only intermediate passes where consumers do not need managed maps.
3. **Bound retained chunk data.** Add a cache policy based on distance, memory and in-flight readers. Preserve player changes/stable tree identities independently and keep existing terrain handoffs valid. Retention changes need lifecycle work and cannot be achieved through collector settings alone.
4. **Test automatic scheduling with realistic headroom.** Compare an actual player frame-rate cap at the intended target against the current uncapped configuration. Then compare the runtime default incremental slice with a 1 ms target slice. Smaller slices are experimental; insufficient collection progress can create growing memory pressure.
5. **Only then test custom scheduling.** Start with automatic mode retained and optionally contribute a modest `CollectIncremental` call during measured spare time. This does not replace Unity's automatic calls, so measure combined GC cost. Consider full manual mode only for a player experiment with memory-pressure monitoring, minimum guaranteed service, increased collection effort/throttled generation when behind, lifecycle restoration of global settings and explicit shutdown/error handling. Never rely only on idle time during sustained traversal. `System.GC.Collect()` is a full blocking collection, not an incremental scheduling tool.

A custom policy must budget GC against whole-frame headroom, not simply whatever remains of the 2 ms streaming allowance. Rendering and gameplay also consume the frame. Skipping GC every busy frame can turn a short pause into a larger later pause or heap growth. Aggressively releasing cached chunks can increase regeneration allocations, so assess memory and revisitation latency together.

## Unity API boundaries

- [`GarbageCollector.GCMode`](https://docs.unity3d.com/6000.4/Documentation/ScriptReference/Scripting.GarbageCollector.GCMode.html) is application-global. Manual/disabled mode changes are not supported in the Editor or WebGL, so the current Editor capture cannot validate a manual policy.
- [`incrementalTimeSliceNanoseconds`](https://docs.unity3d.com/6000.4/Documentation/ScriptReference/Scripting.GarbageCollector-incrementalTimeSliceNanoseconds.html) defaults to 3 ms and is a target, not a hard cap. Collection can fall back to a full cycle under pressure. Very short slices may prevent sufficient progress. Unity can use additional frame slack when an actual frame-rate target/VSync is configured.
- [`CollectIncremental`](https://docs.unity3d.com/6000.4/Documentation/ScriptReference/Scripting.GarbageCollector.CollectIncremental.html) accepts a total work duration and returns whether work remains. Check `isIncremental`; unsupported/non-incremental configurations return false too. Align individual step duration with the intended call allowance rather than assuming a 0.5 ms call will split a configured 3 ms step effectively.
- [`GC tracking`](https://docs.unity3d.com/6000.4/Documentation/Manual/performance-track-garbage-collection.html) distinguishes per-thread CPU allocation totals from all-thread/Editor totals. Use allocation call stacks to find producers; use player captures to assess shipping behavior.
